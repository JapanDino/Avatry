# Правила работы с Git

Единые правила коммитов и ветвления для проекта. Действуют и для человека, и для ИИ.
Цель — чистая, читаемая история, в которой каждый коммит привязан к задаче из `docs/PLAN.md`
и оставляет репозиторий в рабочем состоянии.

---

## 1. Золотые правила

1. **Каждый коммит оставляет репозиторий рабочим.** `web` собирается (`npm run build`), Python-модули импортируются. Не коммитим заведомо сломанное.
2. **Один коммит — одна логическая единица.** Обычно это одна задача из PLAN.md (`0.5`, `1.3`) или небольшая связная группа. Не сваливаем несвязанные изменения в один коммит.
3. **Коммит привязан к задаче.** В конце заголовка ставим ID задачи в скобках: `(0.5)`. Если задачи нет — коммит всё равно осмысленный и атомарный.
4. **ИИ коммитит только по явной просьбе пользователя.** «Закоммить», «оформи коммит» и т.п. Без этого ИИ готовит изменения, но не коммитит.
5. **Документация прогресса идёт вместе с кодом.** Обновления `PLAN.md` (чекбокс) и `STATUS.md` входят в тот же коммит, что и сама работа, либо в отдельный `docs:`-коммит сразу следом.
6. **Никогда не коммитим секреты, `node_modules`, `.venv`, `artifacts/`.** Они в `.gitignore`. Бинарные ассеты — только через Git LFS (см. §5).

---

## 2. Формат сообщения коммита

Conventional Commits. Заголовок — на английском, в повелительном наклонении, без точки в конце, ≤ 72 символов.

```
<type>(<scope>): <короткое описание> (<task-id>)

[необязательное тело: что и зачем, по-русски можно — детали, контекст, ссылки]

Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
```

- **Заголовок — английский** (грепается, привычно для тулинга). **Тело — можно по-русски**, если так понятнее.
- Футер `Co-Authored-By` ставится, когда коммит сделан с участием ИИ.

### Типы (`type`)

| type | когда |
|------|-------|
| `feat` | новая функциональность |
| `fix` | исправление бага |
| `docs` | документация (`docs/`, README, комментарии) |
| `content` | 3D-ассеты, текстуры, морфы (через LFS) |
| `refactor` | переработка без изменения поведения |
| `perf` | оптимизация (FPS, размер файла) |
| `test` | тесты |
| `build` | сборка, зависимости, конфиги (`package.json`, `requirements.txt`) |
| `chore` | прочее обслуживание (gitignore, структура) |

### Области (`scope`) — по частям монорепы

`web` · `pipeline` · `server` · `assets` · `docs` · `infra` · `deps`

Если коммит затрагивает несколько частей — берём главную либо опускаем scope.

### Примеры

```
feat(web): add 5-slider body morph panel (1.7)
feat(pipeline): generate base body with shape keys (1.3)
content(assets): add CC0 t-shirt proxy mesh (2.1)
fix(web): bind morph influences without remounting model (1.7)
docs: close stage 0 in PLAN, update STATUS (0)
build(web): scaffold Vite + React + Three.js (0.5)
chore: add gitignore, gitattributes and LFS tracking (0.2)
```

## 3. Ветвление

Проект используется через git worktrees, поэтому работа идёт в рабочих ветках, а не прямо в `main`.

- **`main`** — всегда собирается. В идеале в `main` попадают состояния, прошедшие контрольную точку (Gate) либо логически завершённый этап. `main` — то, что не стыдно показать.
- **Рабочая ветка** — на этап или на связную группу задач. Имена:
  - `stage-1-body`, `stage-2-garment` — на этап;
  - `feat/web-fit-heatmap`, `fix/clipping` — на отдельную фичу/фикс.
  - Ветки worktree вида `JD/peaceful-...` — машинные, считаем их рабочими.
- **Вливание в `main`**: через PR (если есть GitHub-remote) или `merge --no-ff` локально, по завершении этапа / прохождении Gate. Перед вливанием — `npm run build` зелёный.
- **Мелкие правки документации** можно коммитить в текущую ветку без церемоний.

Не делаем: долгоживущие расходящиеся ветки, коммиты-«свалки», переписывание уже отправленной в `main` истории.

---

## 4. Гигиена истории

- **Атомарность важнее частоты.** Лучше один осмысленный коммит, чем пять «wip».
- Слово `wip` в истории `main` нежелательно. В рабочей ветке допустимо, но перед вливанием такие коммиты лучше собрать (`git rebase -i` интерактивно делает пользователь — у ИИ интерактивный rebase недоступен).
- Не амендим и не форс-пушим уже опубликованные коммиты без явной просьбы.
- Перед коммитом — `git status` и `git diff --staged`: коммитим только то, что осознанно добавили. Никакого `git add -A` вслепую, если в дереве есть постороннее.

---

## 5. Git LFS (бинарные ассеты)

- Под LFS (см. `.gitattributes`): `assets/**/*.glb`, `*.blend`, `*.fbx`, `*.ktx2`, `*.png`, `*.jpg`.
- Перед коммитом ассета — проверить, что он реально ушёл в LFS: `git lfs status` (должен значиться как LFS-объект, а не как обычный blob).
- Крупные бинарники держим **только** в `assets/`. Временные рендеры и скриншоты — в `artifacts/` (в `.gitignore`, в репозиторий не попадают).
- Бюджеты из `CLAUDE.md` (тело ≤ 4 МБ, вещь ≤ 3 МБ) проверяем до коммита ассета.

---

## 6. Чеклист перед коммитом (для ИИ и человека)

1. `git status` — в индексе только нужное, нет секретов/мусора.
2. Затронутая часть собирается (`web`: `npm run build`; `pipeline`: модуль импортируется).
3. Если закрыта задача — чекбокс в `PLAN.md` проставлен, `STATUS.md` обновлён.
4. Сообщение по формату §2, с task-id и (если участвовал ИИ) футером `Co-Authored-By`.
5. Если есть ассеты — прошли через LFS (`git lfs status`) и укладываются в бюджеты.
